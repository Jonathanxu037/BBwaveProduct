单一设备领取奖励限制-v1.1-版本需求说明

更新日期：2026-11-13（GMT+8）适用：v1.1可见角色：产品、开发依据：v1.1 原型和需求开发PRD文档 v1.1（2026-11-13），规则和数值以 PRD 为准

一、一句话概述

两站后台【活动配置】下新增【活动限制管理】，为【活动中心】每个活动（每期）统一配置同设备、同 IP 和领取限制白名单；用户领取和各种发放前按配置判定，超限不发放并提示「奖励领取限制[编号]」。

总原则：同设备、同 IP 只在平台现有技术能力范围内判定（沿用现有设备标识，不接入三方设备识别服务）；各活动原有的同 IP、同设备领取限制上线时迁移到活动限制管理后删除，统一按本栏目配置；与设备、IP 无关的活动自身规则、邀请好友的邀请资格规则和完成任务砸金蛋的每天名额保留，与本需求限制都满足才能领取；前台页面不改，只新增带编号的拦截提示（规则 N9 活动自身规则、N10 设备与 IP 判定、N14 删除与迁移）。

适用范围与两站

作用界定本期管哪些站、端、活动和发放方式。

逻辑
  • 站点：789Bingo、789Games 都做，页面和规则相同；Jira 按站点分别建单（老站【B】、新站【G】）。
  • 端：H5、PC、PWA、iOS、Android 的规则和提示相同；Maya、GLife 小程序同样适用。
  • 活动：【活动中心】的全部活动（含新用户转盘、完成任务砸金蛋），加上 789Bingo 写死使用的另一套返水，列表显示为「返水活动（独立配置）」。Crown Rush（皇冠冲榜）、实物奖品、返现充值转盘和以后新增的活动，进入【活动中心】后同样出现在列表；VIP 奖励尚未开发，开发时接入。
  • 发放方式：用户领取、系统自动发放、充值相关奖励、审核发放、人工发放、批量发放，都按该活动（该期）的配置判定。
  • 不包含：同账户限制；全平台总开关和全平台统一白名单；接入三方设备识别服务（如数美）；拦截记录查询页；被拦截次数统计和风控联动；【活动配置】下其他栏目的活动；前台页面和活动规则说明里的限制提示。
场景方案

幸运转盘（789Games 叫抽奖活动），前台暂定未上线照常列出，可提前配置，前台上线后对领取生效

活动限制管理列表

作用集中展示每个活动（每期）的三项配置，并进入配置弹窗。

逻辑
  • 读取方式：每次进入栏目或点「刷新」，重新读取【活动中心】的全部活动和各期；读取失败沿用后台现有的加载失败提示，不显示过期数据，可再次点「刷新」。
  • 分期一行：分期的活动（有活动列表、可以建多期）每期一行；不分期的活动一个活动一行；分期的活动一期都没有时不出现。
  • 列：活动名称｜期数 / 状态与有效期｜设备限制｜IP 限制｜白名单导入｜操作（「配置」按钮）。
  • 第一列合并：同一活动的多期合并单元格，只显示一次活动名称（菜单名）。
  • 期数重排：按该活动在活动列表里现有各期的创建先后编号，显示「第 N 期」，下方小字为该期的活动名称、状态和有效期；删除某一期后，剩下的期重新编号。
  • 状态与有效期：不分期的活动显示「开启」或「关闭」，下方为「开始～结束」，长期有效显示「长期」；已过结束时间显示「已结束」。有效期与【活动中心】该活动（期）配置页显示的时间一致，列头「?」写明所用时区。
  • 三列配置摘要：设备限制、IP 限制显示「不限制」（未勾选或数量为 0）、「周期 · N 次」（单次领取类）、「周期 · 最多 N 个账号」（多次领取类）；白名单导入只显示「已导入 N 人」或「未导入」。「本活动白名单用户也受此限制」不在列表显示。
  • 排序：按【活动中心】的菜单顺序；同一活动按期数倒序（最新一期在上）。
  • 活动名称下拉：选项为「全部」和列表中的每个活动，默认「全部」，每次读取【活动中心】后更新；选择后点「搜索」，只显示该活动的全部行，列表回到第 1 页。「刷新」保留当前选择，所选活动已删除时回到「全部」。
  • 分页：沿用后台现有分页组件，每页 20 条，可切换为 50 条；没有数据时显示「暂无数据」。

配置限制弹窗

作用为一个活动（一期）设置设备限制、IP 限制和领取限制白名单。

逻辑
  • 标题「配置限制 · 活动名称」，分期的活动带期数（如「配置限制 · 老用户充值转盘 · 第 3 期」）；分「设备限制与 IP 限制」「白名单导入」两个区。
  • 设备限制（同设备）、IP 限制（同 IP）各一行：勾选框、限制周期、数量。未勾选时周期和数量置灰。
  • 周期：活动期间（本功能上线后，活动开始到结束累计）、每天（自然日）、7 天 / 15 天（含领取当天往前 7 / 15 个自然日，每天 00:00:00 滚动）、一个月（自然月）；所有活动都可选，默认「活动期间」。
  • 数量：单次领取类为「最多领取 N 次」，多次领取类为「最多 N 个账号」；0–999999 的整数，0 为不限制。领取类型由技术按 PRD 5.1 活动表固定，运营不能切换。
  • 「本活动白名单用户也受此限制」：只在活动自身有名单（参与名单、指定名单、指定奖励名单）时显示，两项下方各一个，默认勾选；不勾选时名单内全部会员跳过该项，其领取仍计入次数和领取账号先后顺序；只在弹窗显示和修改。
  • 白名单导入点保存生效：沿用后台现有白名单导入组件（导入文件、已导入文件下载、导入结果统计），每个活动（期）单独导入，只对本活动（本期）生效；导入后点弹窗「保存」才生效。名单内会员跳过同设备、同 IP 判定，其领取仍计入；与活动自身名单相互独立。
  • 保存：校验通过提示「保存成功」，关闭弹窗，列表该行刷新，对之后的领取和发放立即生效；已发放的奖励不受影响。
  • ×与取消：关闭弹窗，不保存本次对设备限制、IP 限制的修改，本次导入的白名单也不生效。
场景方案
勾选后数量为空单次领取类提示「请输入最多领取次数」，多次领取类提示「请输入最多账号数」，不能保存
填 -1、1.5、1000000、abc提示「请输入 0–999999 的整数」，显示在输入框下方，焦点停在出错的输入框
填 0 或 999999可以保存；0 为不限制
活动进行中修改数量或周期已领取次数和已绑定账号不清零，按新设置判断；例：单次领取类次数 3 改为 1，已领 2 次的设备不能再领
单次领取类取消勾选后又重新勾选取消勾选期间成功发放的次数同样计入
打开弹窗期间该活动（期）在活动中心被删除，点「保存」不保存，沿用后台现有的保存失败提示；刷新后该行消失

新一期沿用上一期

作用新建或复制生成的一期默认带上已有防护，避免空窗。

逻辑
  • 在活动中心新建或复制生成新一期后，点「刷新」或重新进入，新一期出现在列表，默认沿用同一活动上一期当时的配置：设备限制、IP 限制（勾选、周期、数量）、「本活动白名单用户也受此限制」和领取限制白名单的名单。
  • 「上一期」：同一活动里在新一期之前创建、离它最近的一期（含已结束、已关闭的期，不含已删除的期）。
  • 新一期的领取次数和已绑定账号从 0 开始；之后分别修改新旧两期，互不影响。
  • 没有上一期（第一期）或新建的不分期活动，默认不限制：三列显示「不限制」「不限制」「未导入」。
场景方案
老用户充值转盘新生成第 4 期三列和弹窗设置与第 3 期相同；修改第 4 期并保存后，第 3 期不变
新一期需要不同的限制或名单建期后到本栏目选该活动搜索，核对并修改
在活动中心新建一个不分期的活动刷新后出现，显示为不限制

判定顺序与拦截提示 L01–L03

作用统一每次领取或发放前的判定顺序、拦截处理和提示。

逻辑
  • 顺序：活动现有校验（活动资格、单账号领取规则）→ 领取限制白名单 → 同设备 → 同 IP；只判断已勾选且数量大于 0 的项，命中即拦截，不再判断后面的项。
  • 活动现有校验不通过：按活动现有方式处理和提示，不做本判定。
  • 单次领取类（每个账号只能领一次）：该设备或 IP 本周期内已领取次数 ≥ 最多领取次数时拦截；次数 = 本活动（本期）成功发放的次数，该设备或 IP 上所有账号合计。
  • 多次领取类：按前 N 个账号判定，见「多次领取类：前 N 个账号与绑定」。
  • 不同活动、同一活动的不同期分别计算；新建或复制生成的活动（期）从 0 开始。
  • 拦截处理：不发放；不扣参与次数或抽奖机会；不计次数；按钮保持可点。转盘、抽奖在转动前拦截；签到被拦截时不记签到，连续签到天数可能因此中断。
  • 提示：Toast「奖励领取限制[编号]」，英文「Reward claim limit [L01]」（L02、L03 同格式）。L01 = 同设备达到上限；L02 = 同 IP 达到上限；L03 = 需判定的设备标识或 IP 取不到。
  • 并发：同一设备或同一 IP 的多个账号同时领取，合计不超过上限；同一账号重复点击只发放一次；绕过前端直接调接口同样拦截。
场景方案
KYC 认证送彩金 · 同设备 · 活动期间 · 1 次，账号 A 已在设备 X 领取账号 B 在设备 X 领取被拦截（L01）；在设备 Y 可领
绑定手机号码 · 同 IP · 每天 · 3 次，当天已有 3 个账号领取第 4 个账号被拦截（L02），次日可领
同设备、同 IP 都达到上限只提示 L01
需判定的项取不到设备标识或 IPL03，不发放、不扣次数，可再次点击；不需判定的项（未勾选、数量为 0、白名单会员）取不到时不受影响
未完成 KYC、已达活动自身单账号次数只出现活动现有提示
判定通过但发放失败、网络断开或请求超时沿用活动现有处理；未发放成功的不计次数

多次领取类：前 N 个账号与绑定

作用一个账号能多次领取的活动，限制同一设备、同一 IP 上能参与的账号数。

逻辑
  • 适用：一个账号按活动规则能领取不止一次的活动（如签到、充值优惠、转盘、返水、Crown Rush（皇冠冲榜）），数量填「最多 N 个账号」；N = 1 即只有首个领取的账号能领取。
  • 判定口径：本周期内在该设备（或 IP）成功领取过本活动的账号，按首次成功领取的先后取前 N 个；已满 N 个且当前账号不在其中时拦截（同设备 L01，同 IP L02），未满 N 个时可以领取。「7 天」「15 天」滚动窗口同样按窗口内首次成功领取的先后取前 N 个。
  • 前 N 个账号自己的多次领取按活动原规则，不受次数限制。
  • 同设备、同 IP 分别绑定、分别计数；已绑定账号换到其他设备或 IP 领取，按该设备或 IP 判定，通过后也绑定到该设备或 IP。
  • 周期：「每天」「一个月」在下一个周期开始时清空，重新按领取先后取前 N 个；「7 天」「15 天」按领取当天往前 7 / 15 个自然日的窗口；「活动期间」整个活动期间累计。
  • 重新勾选或调小账号数：保存后只保留前 N 个，其余已领取的账号从保存起被拦截；取消勾选期间成功领取的账号同样计入先后顺序。
  • 调大账号数：按同一先后顺序取前 N 个。
  • 领取限制白名单会员、按「本活动白名单用户也受此限制」跳过该项的名单会员，不受账号数限制，他们的成功领取同样计入先后顺序；审核强制通过的发放不计入。
场景方案
设备、IP 都为「每天 · 最多 2 个账号」，A、B 当天先后在设备 X、IP 1 领取A、B 当天可继续按活动规则领取；C 用设备 X 被拦截（L01），用设备 Y、IP 1 被拦截（L02），用设备 Y、IP 2 可以领取
不限制期间 A、B、C 先后在设备 X 领取签到，改为「活动期间 · 最多 1 个账号」并保存只有 A 可继续领取，B、C 被拦截（L01）
同上，再改为最多 2 个账号A、B 可领取，C 被拦截（L01）
「7 天 · 最多 1 个账号」，A 最后一次在设备 X 领取是 2026-11-04B 在 2026-11-10 领取被拦截，2026-11-11 可以领取
「最多 1 个账号」，A、B 在设备 X 同时首次领取只有一个成功并绑定设备 X
签到被拦截不记签到，次日 00:00:00 后按签到先后重新绑定

充值相关奖励

作用避免用户付款后才发现拿不到优惠，同时保证充值到账不受影响。

逻辑
  • 充值页可选的优惠（充值活动、新用户充值活动计划）：选择时判定，超限时该优惠置灰，下方显示「奖励领取限制[编号]」，可不选优惠继续充值；到账发放前再判定一次，取这笔充值发起时的设备标识和 IP，超限或取不到时不发放该优惠，充值金额照常到账，不通知。
  • 到账或完成 KYC 后自动发放的（每日首充、新用户首充）：充值页没有可选项，发放时按自动发放判定。新用户首充的次日奖励跟随首充奖励：首充奖励已发放的账号，次日奖励不再判定、不计次数；首充奖励被拦截的账号不发放次日奖励。
  • 资格由充值获得的（老用户充值转盘、返现充值转盘）：获得资格时判定，取这笔充值发起时的设备标识和 IP；被拦截时不给转盘次数、不弹出转盘、不提示，充值金额照常到账；充值前不提示。
场景方案

自动发放

作用没有用户点击的发放同样受限制。

逻辑
  • 系统自动发放（如设为自动发放的登录送彩金、邀请奖励、新盈利活动 V2（789Games 叫新输返活动））发放前按同一顺序判定。

审核、人工、批量发放与强制通过

作用后台补发和审核不能绕过限制，同时给审核留出放行口。

逻辑
  • 审核发放（如充值活动设为「审核发放」）：申请时判定一次，被拦截不生成申请，Toast 与用户领取相同；审核通过、发放前再判定一次。
  • 审核时被拦截：【派奖审核】和该活动「活动统计」的这条记录显示「奖励领取限制[编号]」，默认不发放，玩家申请记录沿用「未通过」，不另提示。
  • 强制通过：审核人可以强制通过，照常发放，不解除已有绑定，操作人和时间沿用现有审核记录留痕；单次领取类计入已领取次数；多次领取类只放行这一次，该账号不加入已绑定账号，之后再领照常判定。
  • 转盘、抽奖类只在转动前判定；中奖后进入派奖审核的，审核时不再判定。
  • 人工发放（如消费活动）、批量发放（如邀请好友「待发放 / 发放失败」的批量发放）：发放时判定，被拦截的记录显示原因、不随批量发出，不能强制发放；确需发放走现有【修改余额审批】人工加款。
  • 设备标识和 IP 取用户申请或产生该奖励时的记录；没有用户操作的，取最近一次登录的记录。
  • 只触发一次的奖励（KYC 认证送彩金、绑定手机号码）被拦截后不自动补发；确属误伤的走【修改余额审批】人工加款。

设备标识、IP 与登录记录

作用说明「同一设备」「同一 IP」怎么认定，取值从哪里来。

逻辑
  • 同一设备：按平台现有设备标识判定；用哪个标识、取不到时是否改用其他标识，由技术确定。Maya、GLife 小程序按 H5 的方式取浏览器标识作为设备标识。
  • 同一 IP：用户领取按领取请求的 IP；自动发放取最近一次登录的 IP；充值相关取充值发起时的 IP。连同一 Wi-Fi、或移动网络经同一出口 IP（运营商分配给多名用户共用的公网地址）上网的账号，都算同一 IP。
  • 登录记录（【登录日志】或会员操作日志）：已保存设备标识的沿用现有，没有的新增保存，取值与领取判定使用的设备标识一致；保留时长不短于对应活动从产生奖励到发放的时间。
  • 本版不处理：同一设备换浏览器、在浏览器（H5、PWA）和 App 之间切换、清除缓存或重装 App 后被识别成新设备，以现有标识的识别结果为准；对接三方风控服务后再优化。
  • 计数起点：只计本功能上线后的成功发放，上线前的历史领取不计。
场景方案
同一台手机先用 H5、再用 App 领取可能识别为两台设备，本版接受
客户端未上报设备标识，该活动勾选了设备限制拦截（L03）
移动网络下大量用户共用出口 IP同 IP 数量按活动参与规模设置；误伤时调大数量或取消勾选
家人共用设备、同一 Wi-Fi，或线下投注站代办核实后导入该活动（期）的领取限制白名单
