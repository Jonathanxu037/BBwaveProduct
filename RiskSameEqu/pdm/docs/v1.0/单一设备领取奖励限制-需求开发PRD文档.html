    1. 项目概述

    项目说明
    需求描述【活动中心】下的活动按接入方式（N17）在配置页增加「活动奖励领取限制」板块：可勾选同设备、同 IP（C 方式只有同设备），每项设置限制周期（活动期间 / 每天 / 7 天 / 15 天 / 一个月）和最多领取次数，填「0」为不限制。领取和发放前按配置判定，超过次数不发放，前台提示「奖励领取限制[编号]」；一个账号能多次领取的活动，同一设备、同一 IP 只允许首个领取的账号领取（N18）。A 方式的活动可单独导入领取限制白名单，名单内会员不受这两项限制；B、C 方式沿用活动现有名单（N16）。789Bingo、789Games 两个站都做。
    背景与目标用户在同一设备、同一网络下切换多个账号，可重复领取同一活动的奖励。目标：运营按活动限制同设备、同 IP 的领取次数，活动之间互不影响。参考 Wiki《【风控】新用户转盘活动增加同设备领取限制》，扩大到活动中心的活动，沿用现有设备标识，不依赖数美（三方设备识别服务）。
    多端范围H5、PC、PWA、iOS、Android 的规则和提示文案相同（PC 与 H5 一致）；Maya、GLife 小程序是否适用，以端上能否取到设备标识为准，由技术确认。管理后台改造活动配置页。本版只在现有技术能力范围内判定同设备、同 IP，超出部分以后对接第三方风控服务机构时优化。
    时间与时区GMT+8。「每天」「7 天」「15 天」按自然日（00:00:00–23:59:59），「一个月」按自然月。

    2. 整体业务流程

    2.1 领取判定流程

    运营在活动配置页设置限制（A 方式的活动还可导入领取限制白名单）并保存；领取或发放时按下图判定。

    图中「已达上限」：只能领取一次的活动，判断已勾选且次数大于 0 的项；一个账号能多次领取的活动，该设备或 IP 在本周期内已由其他账号领取过即为已达上限（规则 N18）。D 方式（不改）的活动不经过本流程。拦截时不发放、不扣参与次数；自动发放被拦截时不提示（规则 N6 拦截处理、N8 自动发放）。需判定的设备标识或 IP 取不到时本次不发放，用户领取时提示「奖励领取限制[L03]」（规则 N11）。活动名单会员：该项下方「本活动白名单用户也受此限制」未勾选时跳过该项，勾选时照常判断（规则 N16）。

    2.2 系统时序

    触发执行方动作
    运营保存活动后台 → 后端领取限制和导入的白名单随活动配置一起保存，对之后的领取和发放生效（N13、N15）
    用户点击领取前台 → 后端前台带上现有设备标识；后端记录请求 IP
    收到领取请求或到达自动发放时间后端活动现有校验通过后，按 N5 的顺序（同设备 → 同 IP）判定，通过才发放；自动发放的设备和 IP 取该账号最近一次登录的记录（N8）
    用户充值（获得充值优惠或转盘资格）前台 → 后端记录这笔充值发起时的设备标识和 IP；资格由充值获得的活动（如老用户充值转盘）此时判定，被拦截时不给资格（N7）
    充值到账后端按充值发起时记录的设备标识和 IP 判定后发放优惠；超限或取不到时只到账本金，不通知（N7）
    审核通过、人工发放、批量发放后台 → 后端发放前按 N5 判定，被拦截的记录不发放、显示拦截编号（N19）
    发放成功后端记录账号、设备标识、IP，计入该活动的已领取次数（N3、N4）
    被拦截或取不到设备标识、IP后端 → 前台用户领取时，前台显示带编号的 Toast（页面底部短暂出现、自动消失的提示条）；自动发放时本次不发放、不提示；均不扣参与次数，不计次数
